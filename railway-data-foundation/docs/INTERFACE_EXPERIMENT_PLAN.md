## 实验对象与职责

`scripts/java/InterfaceLab.java` 是短时外部实验工具。REST端为同一程序启动的回环源服务夹具，不是现有Provider业务接口，也不代表现有共享授权性能。Kafka使用本地原生Broker、独立临时SCRAM生产/消费身份、精确主题和消费组权限；不借用权限管理员生产或消费业务数据。管理员只建立和撤销实验身份及元信息。

底座不处理实验载荷。每条载荷是固定长度合成字节，包含序号和单机单调时钟发送时间，其余为填充。原`port_source_db.container_event`不修改，业务明细不写入底座；输出只保存技术汇总及主题名称。原生集群上的真实平台权限流程由独立完整链路测试验证，不能混用两种实验的证据。

## 场景与控制变量

| 场景 | 现有执行方式 | 正式研究待补充 |
|---|---|---|
| 持续负载 `peak` | 按目标Rate逐条提交同样长度的消息/查询任务 | 根据实际业务基线定义高峰；分档增加负载并延长观察，不把60次/秒称为业务高峰 |
| 突发负载 `burst` | 一次集中提交Count个任务；REST4个客户端工作线程，Kafka异步发送 | 记录实际提交速率、客户端排队与服务端资源，逐步增加规模；不能只看设定Count |
| 间断传输 `intermittent` | 两种接口均在中途暂停提交；Kafka额外关闭消费者、提交观察位点后重新加入同组 | Kafka消费者断开与REST间歇查询恢复语义不同，不能直接进行恢复性能排名；真实断网需统一故障边界与外部客户端重试规范 |

当前共用Count、PayloadBytes、Rate和PauseMs；Kafka实验主题单分区、单副本，REST固定4个工作线程。本地机器、运行时、认证方式、线程、分区、消息大小及测试顺序均需记录。当前先跑REST再跑Kafka，会受到预热和系统活动影响；正式实验至少重复3轮并交替顺序，原始结果保留，失败轮次单独说明。

脚本最大2000条、单条64–65536字节、Rate最高1000、暂停100–10000毫秒。这是有界工具范围，不是系统容量结论。REST客户端不做失败自动重试，Kafka单批发送使用完整确认；不要把两种接口的内部重试差异隐藏。

## 输出指标口径

| CSV字段 | 含义 |
|---|---|
| offered / received_unique | 实际安排的任务数 / 按实验序号去重后的接收数 |
| errors / duplicates | 已观察的失败 / 重复接收次数；不是业务处理幂等证明 |
| payload_bytes | 成功唯一接收的载荷字节，不含协议、认证或网络开销 |
| elapsed_s / received_per_s | 消费/源服务就绪后至最后接收的时间及有效接收速率；含提交间隔及指定暂停，首个请求连接开销仍包含在内 |
| p50_ms / p95_ms | 从本机任务提交到接收的延迟分位数，使用单调时钟；不是跨机器端到端时钟方案 |
| drain_ms | 最后一次提交/发送刷新完成后，剩余接收完成的等待时间；0不表示此前从无积压 |
| max_unconsumed_sample | Kafka“已安排任务数减已接收数”的最大采样值，可能包含未确认发送；不是Broker按提交位点计算的消费积压。REST当前未采集此项，0不能解释为无排队 |
| pause_ms | 本次指定暂停时长；实际恢复延迟仍须看原始结果 |

源端CPU、内存、连接数、Broker真实消费积压、断网丢失/重读、授权开销、长期补报和故障恢复分布尚未采集。这些是正式研究需要补齐的测量项，不能用当前CSV代替。

## 运行方式

在`railway-data-foundation`目录：

```powershell
./scripts/start-local-kafka.ps1 -Offline
./scripts/run-interface-lab.ps1 -Count 180 -PayloadBytes 512 -Rate 60 -PauseMs 1500
./scripts/test-interface-tools.ps1
```

结果保存到`.runtime/interface-lab/<时间>/results.csv`和`scope.txt`。失败不会输出成功结论，已完成的原始行仍保留供诊断。Windows下在线删除主题已发生实际故障，工具撤销测试身份与ACL，并把保留主题写入`retained-topics.txt`；没有宣称已清理其载荷。目录与文件均被Git忽略。

## 下一步研究验收

1. 确定Linux环境和地址，验证固定集群的健康、启停、身份/ACL/消息/提交位点跨重启保留及主题清理。不能把Windows失败或临时集群成功记为稳定部署完成。
2. 明确业务场景的量级、消息大小、延迟要求、是否允许历史回放、授权范围及间断传输定义。没有这些输入时，先记录实验假设，不编造业务需求。
3. 在独立实验源上给现有Provider准备同一批任务，使用真实管理员审批与需求方凭据；对齐REST字段/时间范围和Kafka整主题范围，说明查询与事件订阅的不同业务语义。
4. 增加观测和故障注入，跑重复实验，输出延迟曲线、接收速率、积压及恢复曲线，保留失败和异常。
5. 形成接口选择表：按需查询、持续事件、高峰缓冲、间断恢复分别给出适用条件、观测证据和限制。CDC和只读查询是否加入须单独明确；本轮没有扩大其实现范围。
