# 接收监测配置与本方操作记录

> 管理员现使用一个“传输监测”页面，REST与Kafka同表展示。页面操作及统计耗时口径见[统一监测指南](TRANSFER_MONITOR_GUIDE.md)；下文保留独立技术补报的配置说明。

## 角色入口

| 角色 | 入口 | 能查看的内容 |
|---|---|---|
| 管理员 | 运行监管 → 传输监测 | REST与Kafka技术记录、统计、详情；采集状态与订阅摘要抽屉 |
| 提供方 | 数据发送 → 发送记录 | 归属于本主体来源的发送记录、回执及失败原因 |
| 需求方 | 数据接收 → 指定任务 → 任务日志 / 接收进度 | 本主体任务的操作、落库、去重、位置提交、补报及异常 |

供需双方没有独立平台监测菜单，也不能通过直接输入 `/kafka-monitor` 进入监管页面。管理员不能查询需求方消息、下载业务文件或获取需求方数据库连接。双方原有记录接口继续执行主体范围检查；隐藏菜单不是后端权限控制的替代。

## 管理员怎样核对传输

1. 统一列表按传输方式、处理阶段、资源、结果和时间筛选，点击“详情”查看固定原因及分区位置。Kafka发送成功不等于需求方落库。
2. “接收落库”阶段展示新增数量、去重和事务提交耗时；历史未采集保持未知。
3. 通过“采集状态与订阅摘要”抽屉查看补报状态及逐授权消费摘要。原四个管理地址兼容跳转，不再新增独立菜单。

所有接收事件标为“接收端自报”。它是技术观察，不是可信计费或业务处理成功证明。底座关联的主体、资源、能力和主题由授权记录确定，上报方不能覆盖。最近事件仅代表当时状态；没有事件不补成零，不推断为实时健康或实时积压。

## 供需双方怎样操作

提供方继续选择源记录并单条或勾选发送；“发送记录”在当前页面抽屉打开，正在批量发送时不可打开。历史回执与本次发送结果分别展示。重复发送同一业务记录会产生新Kafka位置。

需求方在接收任务行点“任务日志”，在当前页面抽屉查询该任务。关闭抽屉、切换任务或退出登录会隔离晚到响应、清空内容，不停止后台接收任务。本主体在撤权后仍可查询已保留的任务历史。

日志和页面支持10/20/50项分页、展开详情、手动或每5秒刷新；页面隐藏暂停自动刷新，失败清空旧表并允许重试。显式演示不会读取真实日志。

## 过程事件与可靠性

- 创建、启动/恢复/停止请求、凭据更新：事务已受理页面操作，保留实际账号编号。
- 重启恢复、连接就绪、停止、重试、阻塞：后台的真实状态转移，不把用户发出请求当成后台已完成。
- 批次落库：消息、数据库检查点、消费摘要、过程日志及监测队列在同一数据库事务内保存；失败整体回滚。
- 位置提交成功/待确认：Kafka提交在数据库事务成功后执行。进程中断、提交超时或回执日志缺失时保持未知，不能宣称全局恰好一次。
- 消费摘要确认/待补报/拒绝：保留原订阅凭据及授权校验规则，不回滚已落库消息。

新增监测上报走独立服务端技术凭据，与登录会话、REST令牌、Kafka密码和订阅技术令牌分离。撤权、到期或主体停用后，接收仍被阻止，但阻塞事件可以继续上报管理员。新凭据没有任何数据访问、审批、凭据领取或Kafka权限。

已有真实过程日志通过追加迁移加入补报队列；升级前不存在的过程不补造。临时上报故障使用有上限的退避重试，事件编号保持不变；内容冲突或永久格式错误隔离保留。同编号同内容去重，不改写第一次收到的时间。监测补报本身不再递归产生待上报日志。

数据库完全不可用期间无法持久写入日志。提供侧现有有界采集/补报也可能有缺口，管理员查看待补报、丢弃、隔离和存储失败状态；不能将现有记录宣称为无损全量审计。

## 接口与存储

- `POST /api/v1/telemetry/receiver-reports`：`X-Receiver-Telemetry-Token`服务端认证，`{events:[...]}`最多50个固定结构技术事件；返回确认事件编号、新增及重复数量。禁止消息内容、任意错误文本、前端主体归属或主题覆盖参数。
- `GET /api/v1/kafka-transfer-events`：仅真实管理员。参数`grantId/taskId/eventType/outcome/from/until/limit/offset`，时间为UTC含下界、不含上界；每页1–50、偏移不超过1000000。响应`{code,message,data:{items,total,configured,source,last_received_at}}`。未登录401、普通角色403。
- `GET /demand/api/v1/receiving-tasks/transfer-logs?taskId=...`：仅需求方本主体，供任务抽屉使用，列表和总数按主体过滤。
- 发送记录继续使用`/api/v1/runtime-events?collectionPoint=KAFKA_PRODUCER`，原来源归属检查不变。

底座V18建立`foundation_db.kafka_receiver_event`，只保存技术元信息；需求方V3建立`demand_receiver_db.receiving_monitor_outbox`，与原`receiving_transfer_log`关联。最新底座V19、需求方V4为技术日志追加可空批次入库耗时列，历史不回填。消息内容始终留在需求方`received_message`，不经过底座。

当前没有过程日志自动归档/清理或导出功能。数据库备份需同时保留任务、消息、检查点、原消费摘要队列、过程日志及新增监测队列。Docker文件日志轮转和Kafka消息保留不是这些数据库表的保留配置。

## 首次配置或升级

Windows在项目目录显式执行：

```powershell
./scripts/enable-receiver-monitor.ps1
```

仅追加随机监测凭据和固定节点编号，不打印秘密，不改原数据库密码、加密主密钥或账号。原配置备份在忽略的本机运行目录内；重复执行核对原值，不自动轮换。先更新启动底座，再更新启动需求方服务。底座新接口未配置时明确显示未接入，需求方消息接收不依赖监测上传成功。

部署环境变量：底座`FOUNDATION_RECEIVER_TELEMETRY_TOKEN`、`RECEIVER_TELEMETRY_NODE_ID`；需求方`DEMAND_TELEMETRY_TOKEN`、`DEMAND_TELEMETRY_NODE_ID`。两端令牌相同，必须与Provider控制令牌不同。禁止放入任何VITE变量或聊天。

Linux新建环境的部署初始化自动生成独立配置。已有私有配置使用：

```bash
sudo python3 deploy/linux/manage.py enable-receiver-monitor
sudo docker compose -f deploy/linux/compose.yml build foundation demand web
sudo docker compose -f deploy/linux/compose.yml up -d --wait --wait-timeout 300 foundation
sudo docker compose -f deploy/linux/compose.yml up -d --wait --wait-timeout 300 demand web
```

升级命令先验证原私有配置、保存备份，再更新配置摘要。原状态不一致时拒绝；不得删除`.private`或更换密钥重建。异常中断时先用`monitor-upgrade-backup`核对恢复原配置，不手工跳过完整性校验。云端容器运行仍须按部署手册实际验收。
