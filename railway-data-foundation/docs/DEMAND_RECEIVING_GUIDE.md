此模块执行真实 Kafka 消费和 MySQL 落库，不是消息预览或模拟接收。统一前端进入需求方“数据接收”；数据执行后端是独立 `demand-service`。

```text
业务源 → 提供方业务服务 → Kafka → demand-service → 需求方数据库
                               ↕
                          统一前端需求方工作台

foundation-service：登录、主体、审批、授权核验、技术摘要
```

业务消息不经过底座后端、不存入 `foundation_db`。前端消息查询由 `/demand` 直接路由到需求方服务。正式部署应将该服务、数据库、数据库账号和加密密钥放在需求方接收环境，反向代理分别配置 `/api` 与 `/demand`；控制通道与业务通道分开。本机使用同一台机器和 MySQL 实例中的不同数据库便于开发，不代表生产部署共用数据权限。

## 启动

在 VS Code 工作区根目录的 PowerShell 终端执行：

```powershell
.\railway-data-foundation\scripts\start-local.ps1 -Kafka -Demand
```

首次增加需求方服务或更新代码，可先执行：

```powershell
.\railway-data-foundation\scripts\start-demand-local.ps1 -Build -Offline
```

完整代码更新仍需重新构建和启动底座，新增授权核验接口才生效。前端保持原工程：

```powershell
cd .\railway-data-foundation\foundation-web
npm install
npm run dev
```

也可使用 VS Code“启动完整系统（前端 + 三个服务 + MySQL + Kafka）”。端口：前端5173、底座18080、提供方18081、需求方18082。

本机脚本初始化独立 `demand_receiver_db` 和 `demand_receiver_app`，并生成随机数据库密码和独立32字节加密密钥，保存在被Git忽略的 `.env.local`。不修改原数据库账号密码。已有接收库但缺少加密密钥时拒绝重新生成，必须恢复原密钥。

接收进程通过显式环境白名单启动，不继承底座、源库或Broker运维凭据。UTF-8运行日志仅写入 `.runtime/local/demand.out.log`，关闭业务请求/响应调试输出并限制日志轮转容量。启动构建只执行不访问数据库的单元测试；集成测试由独立测试命令执行，并强制使用测试库名称。

## 操作链

1. 需求方申请 Kafka 整主题订阅，所属提供方确认，管理员最终审批并配置 Broker 权限。
2. 需求方一次性领取凭据。点击“配置接收任务”可在内存中转交密码及技术令牌；或者进入“数据接收”手工填写已领取的两项凭据。二者不能互换。
3. 填写任务名称、已授权订阅和首次接收起点，创建任务。首次默认“可保留历史”，也可选“仅新消息”。后续启动、恢复不能重新选择起点。
4. 点击“启动”。后台从真实 Kafka 接收消息，事务提交到需求方数据库后才提交 Kafka 消费位置。
5. 点击“查看数据”查询已落库消息，按主题、分区、接收时间筛选；“查看内容”显示消息键、内容与有序消息头。JSON格式化显示，文本按原内容显示，非UTF-8内容用Base64表示，空值与空字节区分。
6. 页面关闭或退出登录不会停止任务。主动点击“停止”才停止本地任务；授权撤销、到期或治理核验不可用也会暂停读取。
7. 网络或数据库故障自动有限重试；阻塞后处理原因并点击“恢复”。凭据重新签发后，先停止并等待连接释放，再“更新凭据”，保留已有数据和检查点。主题或集群身份变化不能覆盖原任务。

任务停止不等于底座撤权：停止只控制本需求方接收程序，底座订阅撤权仍在“我的 Kafka 订阅”完成。历史已交付数据保存在需求方数据库，不因撤权删除。

## 真实存储位置

本机MySQL `127.0.0.1:13306` 中：

| 库 / 表 | 用途 |
|---|---|
| `foundation_db` | 底座治理元数据，没有接收消息内容 |
| `port_source_db` | 原提供方业务源，现有广州港示例是模拟记录 |
| `demand_receiver_db.receiving_task` | 任务、真实主体、连接元信息与加密凭据 |
| `demand_receiver_db.received_message` | 完整消息键、内容、头、分区位置与接收时间 |
| `demand_receiver_db.receiving_checkpoint` | 事务内持久化的下一消费位置 |
| `demand_receiver_db.receiving_outbox` | 可重试的技术摘要，不包含消息内容 |

需求方服务账号只获得自身数据库权限，不授予业务源或底座库权限。不得为了查看消息给管理员或提供方开放本服务的业务接口。

## 可靠性与范围

- 关闭自动提交，消息、检查点、摘要补报记录在同一事务保存，之后提交Kafka位置。
- 数据库失败不会提交位置；数据库成功但位置提交失败时可能重读，按授权、主题实际身份、分区、位置幂等落库。同位置内容不一致时阻塞。
- 服务重启恢复用户期望运行的任务；已阻塞任务等待人工恢复。恢复位置已被Kafka清理时拒绝静默跳过。
- 单实例最多4个并行任务，其他任务等待启动；同一个授权只建立一个任务。不要让其他消费程序同时占用该授权专属消费组，否则会发生分区分配竞争。
- 撤权检查在每批落库前进行，空闲时至少每3秒检查。已经通过核验的在途事务可能完成，不保证追溯收回已交付数据。
- 摘要只有分区、位置、条数、字节和观察时间。补报复用固定报告编号；永久拒绝保留为REJECTED，不伪造确认。它是自报观察，不等同于可信计费。
- 保存到通用接收表不等于完成业务计算或写入特定业务表；不宣称跨Kafka/MySQL全局恰好一次、CDC、自动全表发送、多实例高可用或稳定生产部署。
- 只有提供方实际发送到主题的消息才会被接收。资源发布、授权、启动任务不会自动扫描或发送业务数据库全部行。
