## 1. 当前问题

现有提供服务向 `port.container.event.v1` 生产完整 `container_event` 事件；底座已支持 Topic 元数据验证与提供侧新发送的启停控制（[交付](KAFKA_RUNTIME_CHANGELOG.md)），仍不授予需求方订阅权限。原 REST 策略的允许字段和数据时间范围由提供服务逐请求执行，Kafka Broker 则按身份、主题和消费组控制读取，无法直接对同一 Topic 内的每条消息按这些属性过滤。

Kafka 标准消费者授权包括主题读取/描述及消费组读取，详见 [Apache Kafka 3.9 权限与 ACL 官方说明](https://kafka.apache.org/39/security/authorization-and-acls/)。本项目依赖 Kafka 3.9.1，测试直接验证实际 Broker 行为。正式运行版本与部署安全配置须单独确认，测试依赖不代表已经部署生产集群。

不能将某个 REST 关系直接变成整个 Topic 的读取权限，不能把 `rdf_` 调用令牌当 Kafka 登录密码，也不能仅把底座状态改成“启用”就宣称 Broker 已执行授权。

## 2. 需要明确的共享粒度

| 方案 | 实际允许范围 | 后续工作 |
|---|---|---|
| 整主题授权（建议先实现） | 指定 Topic 中完整消息及可访问历史；授权有效期限制访问时间，不过滤消息内的数据时间 | 独立整主题审批、独立 Broker 凭据、每个授权专属主体和消费组、权限生效/撤销确认 |
| 字段/数据时间范围共享 | 仅符合审核范围的字段和事件 | 提供侧建立并维护隔离 Topic，执行字段投影与时间筛选，控制历史消息、生命周期和订阅权限 |

用户已明确选择整主题授权：单独审批后允许完整消息及历史，先完成授权与撤回闭环。本轮完成审批登记，下一步执行Broker权限；现有 REST 关系和策略继续按原范围执行。

## 3. 已交付的 Broker 基础验证

新增 `examples/kafka-demand/`，独立于底座和提供服务的 Maven 工程，不加入聚合业务服务。测试使用随机端口、随机凭据和随机主题的临时 KRaft Broker：

- 外部监听在本机，SASL/PLAIN 用于可重复的本机认证测试，`StandardAuthorizer` 默认拒绝无 ACL 请求。
- 控制器监听同样仅本机；测试控制器需要匿名超级用户，不能复制成公开部署配置。用户面对的 SASL 监听不允许未认证身份读取业务主题。
- 只授予精确主题的 `READ/DESCRIBE` 和精确消费组的 `READ`，没有写入、创建主题、集群管理或通配主题权限。
- 使用真实消费者验证允许、错误密码、未授权主题/消费组、无 ACL、直接分区读取绕过尝试及移除 ACL 后已建立连接的后续拒绝。
- 独立订阅可执行程序只输出主题、分区、位点和消息载荷字节，不输出消息键/业务内容；不提交位点，不上报消费侧指标，不宣称业务已完成处理。

ACL 帮助类仅用于隔离验证的精确增删。一个用户名对同一 Topic 的主题权限会被多个消费组共用，不能直接作为多共享关系的生产协调器。后续优先每份授权使用专属 Broker 主体；否则必须按所有有效授权的并集协调，不能撤回一份关系就误删其他授权。

测试停止 Broker 后由 TestKit 清理专属临时文件；不删除正在运行 Broker 的主题，避免 Windows 文件映射导致的重命名失败。它不读取 `port_source_db`、不改变原 Topic、底座表或关系，不需要 Docker。

## 4. 后续底座联动设计要求（尚未实现）

如果选整主题授权，接口需明确记录该范围及人工批准，不能伪装成已有字段/时间策略。管理元数据包含双方主体、资源/能力、明确 Topic、专属消费组、Broker 主体引用、有效期、申请/批准/执行状态、版本和变更原因。

Broker 执行采用运维受信任的管理员客户端，动态创建或轮换独立 SCRAM 凭据，精确增删 ACL。底座不消费消息，凭据不得出现在普通查询、日志或前端构建变量中；签发结果一次性展示，后续撤销/轮换。

需区分“审批已通过”和“Broker 权限已生效”。数据库事务与 Broker 操作不能假装是一个事务，使用可重试的执行状态和幂等操作，核对治理版本并处理失败补偿。共享暂停/撤回、主体/资源来源停用、能力停用和到期都必须进入撤销链路。

静态 SCRAM 和 ACL 本身不保证到期自动失效，也不保证控制服务故障时立即撤销。因此到期/故障处理、执行时延及状态必须明确验证；收到 Broker 撤销确认前不能展示“已完全撤销”。不得用现有 REST 的即时逐请求语义描述异步 ACL 协调。

Topic 中历史消息和已交付/已缓冲记录不会因撤销而被追回。消费计量与生产计量分别记录；两者不能相加当作共享总量，暂时没有消费侧采集时仍显示未知。

如果选字段/时间方案，应先建立提供侧隔离数据通道，再复用上述身份和 Broker 授权；不能通过需求方消费后过滤来实现保密。

## 5. 启动与验证

从项目目录执行：

```powershell
# Java 17 + Maven，自动启动和停止独立临时Broker
powershell -NoProfile -ExecutionPolicy Bypass -File ./scripts/test-kafka-demand-example.ps1 -Offline
```

连接已经由运维配置好 SASL/SCRAM、TLS、精确主题/消费组权限的外部 Broker：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File ./scripts/run-kafka-demand-example.ps1 `
  -Brokers '实际Broker域名:9093' -Topic '实际主题名' -Group '已授权消费组' `
  -Username '独立Kafka用户名' -Protocol SASL_SSL -Mechanism SCRAM-SHA-512
```

脚本构建示例并安全提示输入 Kafka 密码，仅向订阅子进程注入 Kafka 配置，不传递本机 Source/底座数据库密码或服务间令牌；密码不写入参数或文件。默认只观察新消息，最多15秒/10条；可设置 `-Seconds/-MaxMessages`。正式 Broker 未运行或未授权时会明确失败，不自动启动未认证 Broker，也不回退模拟成功。本机实验 `SASL_PLAINTEXT` 只接受 localhost/127.0.0.1/回环IPv6 地址。

当前启动示例不是底座签发订阅权限的入口。现有 `start-local.ps1` 不会启动常驻 Kafka；提供侧能力启停和整主题审批已交付，订阅凭据及Broker权限执行联动仍待开发。
