# 统一传输监测使用指南

## 入口与操作

管理员登录后进入“运行监管 → 传输监测”。原调用审计、调用追踪、共享计量、Kafka传输监测四个菜单合并为一个页面，不再分REST与Kafka页签。

顶部显示REST接口调用次数、Kafka发送成功消息数、接收新增落库条数、异常事件数。下方一张表按时间倒序展示：时间、数据资源、传输方式、处理阶段、结果、数据量、阶段耗时和详情。可按时间、资源、方式、阶段、结果筛选；“更多筛选”可输入接收任务或追踪编号。

默认当天，查询范围最多24小时。默认范围下刷新持续纳入新事件，跨零点切换当天；人工选择历史时间后保持该范围。自动刷新间隔5秒，页面隐藏暂停，失败停止刷新并显示重试。每页10/20/50条。

统计卡按已查询时间及资源汇总完整已上报数据，不受列表分页、方式、阶段或结果筛选影响。列表结果与总数由同一服务端查询限定，不在浏览器拼接不同来源的分页。

“详情”打开抽屉，查看固定原因说明、数据来源、治理编号、主题、分区位置、批次和接收时间。REST及发送记录可以查看原有追踪过程；没有收发消息关联的记录不虚构成完整端到端追踪。“采集状态与订阅摘要”抽屉保留采集故障、待补报、隔离、丢弃及逐授权消费摘要，普通页面不展开运维细节。

## 统计与耗时的含义

| 名称 | 实际含义 |
|---|---|
| REST接口调用次数 | 已收到的REST执行事件数量，包含成功、拒绝与异常 |
| Kafka发送成功消息数 | 已收到Kafka发送成功摘要中的消息数量 |
| 接收新增落库条数 | 接收端批次落库事件的新增数量；重读去重、位置回执及摘要不重复累计 |
| 异常事件数 | 提供方或接收端结果为ERROR的技术事件数量；不是异常业务消息数或受影响任务数 |
| REST接口耗时 | 提供方接口执行处理耗时，非用户浏览器网络往返时间 |
| Kafka发送耗时 | 提供方发送请求的整体处理耗时，含准入核验、读取源记录、序列化和等待Kafka回执，不是纯网络耗时 |
| 接收落库耗时 | 单调时钟测量批次入库事务开始至提交返回的毫秒数；含入库处理、检查点及队列写入，不含Kafka拉取等待与消费位置提交 |

多需求方各自接收同一消息会分别产生落库计数，发送数与落库数不能直接相减判断丢失。不同阶段的耗时不能相加当成端到端延迟；本轮没有消息跨系统关联和时钟校准。

没有对应来源的已上报事件时显示“—”，不解释为零或实时健康。已有事件中的统计零只表示当前已收到的记录为零，不保证没有上报缺口。接收端事件始终是客户端自报，不作为可信计费或业务处理成功证明。

## 角色与兼容

只有管理员可进入统一监测页。提供方仍通过“数据发送 → 发送记录”查看本方Kafka记录；需求方仍通过“数据接收 → 任务日志/接收进度”查看本主体任务。提供方原REST调用记录等已有权限保持不变。

管理员访问旧`/runtime-events`、`/runtime-traces`、`/metrics`和`/kafka-monitor`自动跳转统一页面；旧追踪编号保留为筛选条件，Kafka旧入口预选Kafka消息。提供方旧记录页面仍按原主体隔离。

接收消息及下载仍通过独立需求方服务提供，管理员不获得业务消息内容、下载权限、连接密码或数据库权限。监测请求不读取业务表。

## API与追加迁移

`GET /api/v1/transfer-monitor/events`仅管理员，未登录401、普通角色403。必填`from/until`为带时区的ISO时间，含起点、不含终点，最多24小时；可选`method=REST|KAFKA`、`stage`、`outcome`、`resourceId`、`taskId`、`traceId`及`limit/offset`。分页最大50，偏移最大1000000。

阶段为`REST_QUERY/KAFKA_SEND/KAFKA_STORE/KAFKA_CHECKPOINT/KAFKA_REPORT/KAFKA_TASK`。统一响应：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "items": [],
    "total": 0,
    "summary": {
      "rest_calls": null,
      "kafka_sent": null,
      "received_records": null,
      "error_events": null
    },
    "receiver_configured": true,
    "source": "REPORTED_TECHNICAL_EVENTS"
  }
}
```

每条记录有稳定`entry_id`、`origin`、`occurred_at`、`method`、`stage`、`resource_id/resource_name`、`outcome`、`reason_code`、`record_count/byte_count`、`duration_ms/duration_scope`及技术关联字段；不含消息键值、头、异常堆栈或秘密。不同来源先UNION再稳定排序、计数及分页；统计与列表在同一只读可重复读事务中读取。查询显式统一旧表与新增表的字符排序规则，兼容已有部署。

底座追加V19、需求方追加V4，只为技术日志增加可空`storage_duration_ms`，没有新建业务表。需求方在事务成功后测量时间，通过同批次位置回执的日志和持久监测队列发送，统一页将它关联到批次落库记录。若进程在提交后中断或无法保存回执，耗时仍未知，不补造值；已提交消息和检查点不回滚，Kafka位置提交规则不变。

历史监测事件不回填耗时，不改变旧事件内容摘要。无耗时字段的旧重报保持原幂等规则；新耗时仅允许位置回执事件携带，内容冲突仍拒绝。

## 升级顺序

保留所有现有私有配置和密钥。先更新并启动底座以执行V19和新查询接口，再更新需求方执行V4，最后更新前端。已有独立监测凭据继续使用，无需重新生成。监测尚未配置的部署仍按[监测配置指南](KAFKA_TRANSFER_MONITOR_GUIDE.md)显式启用。

Windows沿用原本机启动脚本；Docker沿用[部署手册](BAIDU_CLOUD_DOCKER_DEPLOYMENT.md)的构建与有序更新流程。不重建原数据库、不改原`container_event`记录。云端运行和备份恢复仍须在目标服务器验收。
