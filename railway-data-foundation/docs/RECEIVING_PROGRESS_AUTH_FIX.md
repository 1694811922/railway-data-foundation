# 接收进度误跳登录页修复（2026-10-17）

## 原因与处理

网页登录会话与接收任务的Kafka订阅技术凭据是两套不同身份。原需求方`FoundationClient`把底座返回的技术凭据401原样传到浏览器；前端统一登录拦截器据此清空会话、跳回登录页。用户实际仍处于有效登录状态，这属于错误的失败分类。

修复后，需求方服务将订阅技术凭据缺失、格式错误及上游拒绝认证转换为403，窗口提示“接收任务的订阅技术凭据已失效，请停止任务并更新凭据后恢复”。真正的网页登录缺失或过期仍返回401并触发重新登录；上游授权拒绝403和服务不可用503保持原含义。不放宽消费权限，不恢复旧订阅，不忽略前端401。

本次检查时，本机任务处于BLOCKED，其申请仍APPROVED、执行权限REVOKED，技术令牌已清除。原审批和已接收数据保留。若要继续接收，应由管理员确认资源已发布且原审批条件有效、重新配置Kafka权限，再由需求方领取新凭据，停止任务并等待连接释放、更新凭据、手动恢复。重新登录不能恢复已撤回的Kafka身份。

## 修改与验证入口

- `demand-service/.../FoundationClient.java`：按认证通道区分错误，技术凭据失败不冒充网页登录失效。
- `demand-service/.../FoundationClientTest.java`：真实本机HTTP上游夹具，覆盖技术令牌401/格式错误/缺失、真实会话401、403/503及成功响应。
- `foundation-web/scripts/receiving-history-entry-live.mjs`：真实浏览器核对撤权后历史消息入口、进度403保留登录和重试、真实退出后401跳转。
- `examples/kafka-demand/.../KafkaFoundationLiveTest.java`：在生命周期下架清除技术令牌后执行上述浏览器验收，再核对管理员重新配置和新凭据恢复。

不新增数据库表、配置或迁移；只更新需求方运行包。底座仍V20，需求方仍V4，原账号密码及私有配置保留。测试结果在执行结束后记录，不将失败或跳过计为通过。
