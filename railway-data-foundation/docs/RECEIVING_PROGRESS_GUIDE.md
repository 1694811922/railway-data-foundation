# 接收进度与零落库排查

需求方登录后进入 **数据接收 → 接收进度**，点击 **刷新进度** 获取一次真实查询结果。此面板不自动消费消息，不修改消费位置、任务版本或运行状态。

## 如何判断

| 显示状态 | 含义与操作 |
|---|---|
| 主题当前无可用消息 | 各分区最早与末尾位置一致；等待提供方在“数据发送”发送记录。源表有数据不代表Kafka有消息 |
| 尚未建立接收检查点 | 当前分区没有数据库检查点；任务首次启动或新增分区后由实际接收任务建立，页面不猜测起点 |
| 存在待接收位置 | 末尾下一位置高于落库下一位置；结合运行状态判断是否需要启动、恢复或等待重试 |
| 已追平查询时位置 | 已保存检查点到达此次查询的末尾位置；后续新消息仍可继续接收 |
| 快照检查点超出可用范围 | 保存位置低于保留起点或高于当前末尾；先刷新核对任务状态，不自动重置或跳过历史 |
| 查询失败 | 授权、凭据、主题身份或连接无法核验；旧结果被清空，不能解释为没有消息或已追平 |

“已落库消息”为需求方数据库中的实际记录数。“待接收位置差”为末尾位置减去落库检查点；Kafka位置可能存在间隔，不能将位置差当成精确消息条数或计费量。

## 分区字段

| 中文列 | 作用 |
|---|---|
| 分区 | 当前主题中的分区编号 |
| 最早可用位置 | Kafka目前保留范围的起点 |
| 末尾下一位置 | Kafka目前末尾之后的下一位置 |
| 落库下一位置 | 需求方数据库事务保存的下一接收位置，缺失时显示“未建立” |
| Kafka已提交位置 | 获批消费组已提交的下一位置，缺失时显示“未提交” |
| 待接收位置差 | 可用范围内的末尾与落库检查点之差；位置失效或检查点缺失时为“未知” |

面板分别显示检查点读取时间和查询完成时间。持续接收期间两次读取可能存在短暂时间差；诊断不替代任务状态，也不自动阻塞或恢复任务。

## API与权限

`GET /api/v1/receiving-tasks/{id}/progress`，前端通过独立 `/demand` 通道访问18082，继续使用 `{code,message,data}`。

`data`包含 `task`、`topic`、`checkpoint_read_at`、`checked_at`、`summary`、`partitions`。摘要包含 `status`、`partition_count`、`remaining_positions`；分区包含 `partition`、`earliest_offset`、`latest_offset`、`next_offset`、`committed_offset`、`remaining_positions`、`status`。无法确定的数值使用 `null`，不补造0。

仅真实需求方能查看本主体任务。列表中的任务编号不能绕过归属检查；管理员、提供方和其他需求方不能查询这份进度。先读取本主体任务及检查点的一致只读快照，再释放数据库事务，核验该任务的独立技术令牌，并以加密保存的专属Kafka凭据查询元数据。

Kafka使用Admin接口查询主题身份、保留范围及获批消费组位置，网络查询总等待有5秒上限，不创建Consumer、不加入消费组、不poll、不commit。读取后复核主题身份；主题重建、范围变化、凭据失效或底座故障明确拒绝。任务未保存已确认主题身份时不推测旧基准。

授权撤销后不能查询新的Kafka位置；本主体已落库历史消息仍按原规则可查。API不返回密码、技术令牌、原始上下文或业务消息内容。查询失败支持手动重试，切换任务、退出登录或关闭面板会丢弃晚到响应；演示模式不请求真实服务。

## 启动

后端使用原本启动方式；本轮仅更新需求方服务，不新增数据库表或迁移。前端在 `railway-data-foundation/foundation-web` 中执行 `npm run dev`，访问 `http://127.0.0.1:5173`。

真实测试使用独立主题与身份，不向用户当前主题自动发送消息，不修改原container_event。完整验证结果见 [本轮交付](RECEIVING_PROGRESS_CHANGELOG.md)。
